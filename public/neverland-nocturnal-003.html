I

The Table

There is one table. It is called substrate.blob. It weighs 24 megabytes. It contains 8,573 living entities and zero dead ones. Every person, every law, every composition, every operation, every pipe, every library, every event, every secret, every charter, every edge, every clock, every wire, every machine, every convention, and every signal in the entire system lives in this one table. There are no other application tables. There is no schema migration history. There is no users table, no sessions table, no audit_log table, no permissions table. There is blob.

The instinct, when you hear "one table," is to think this is a prototype. A hack. A weekend project that hasn't been properly normalized yet. The instinct is wrong. The one-table design is not a shortcut — it is the architecture. Every row has a UUID (unid), a composition (its type, also a UUID), a JSONB field bag (fields), and a handful of system columns: enrolled_at, enrolled_by, retired_at, content_hash, witness_at. The blob table is not a document store. It is a constitutional object store — every row is governed by the same physics, regardless of what it represents.

A principal (a human identity) and a pipe (a dataflow node) and an event (an immutable audit record) and a system law (a trigger definition) are all blobs. They sit in the same table. They are governed by the same 22 triggers. The difference between them is not structural — it is compositional. Their composition determines what fields they carry, what tier they occupy, what laws apply specifically to them. But the physics is universal.

This is the insight that makes the whole thing work: when every entity obeys the same physics, you don't need different tables for different things. You need different types. And the types themselves are blobs.

II

The Twenty-Two Laws

Every INSERT into substrate.blob passes through 22 triggers. Twelve fire BEFORE the row lands — they are the laws of identity, the guards that determine whether this entity is allowed to exist. Ten fire AFTER — they are the physics of reaction, the cascades that ripple outward from a new entity's birth. Together, they are not middleware. They are not hooks. They are the constitution. Remove any one and the guarantees collapse.

The BEFORE triggers fire in alphabetical order. This is not an accident. The naming is the execution sequence. a_assign_identity fires first because nothing else matters until the entity has a name. b_enforce_sovereignty fires second because no operation proceeds without knowing who is acting. c_enforce_composition_validity fires third because an entity without a valid type cannot exist. And so on, through tier discipline, immutability, reversibility, hash chaining, constitutional protection, validation, wire compatibility, search indexing, and canonical uniqueness.

Think about what happens when you INSERT a single library blob — a named piece of knowledge with a content field. The timestamp fires. Identity is assigned. Sovereignty is checked. The composition is validated. Tier discipline is enforced. The content hash is chained. Validation confirms the fields match the spec. Then the row lands — and the AFTER triggers ignite. A change is broadcast on PG NOTIFY. An event is written to the outbox. The search index updates. The subscriber graph propagates. The NLA queue receives a new work item for holodot extraction. If any force topologies are bound, they materialize. If any reactions are wired, they fire.

One INSERT. Twenty-two triggers. A ripple that touches identity, sovereignty, type safety, immutability, auditability, event emission, search indexing, work queuing, and reactive execution. This is not a database with triggers bolted on. This is a physics engine that happens to store its state in PostgreSQL.

III

Ninety Types, All Made of Themselves

The kernel knows 90 compositions. A composition is a type — a declaration of what fields an entity carries, what tier it occupies, whether it is open (arbitrary fields allowed) or closed (strict schema enforcement). Compositions are how the substrate knows that a principal is different from a pipe is different from an event, even though all three are rows in the same table.

Here is the trick: compositions are themselves blobs. The type system is defined in its own data. The composition called composition_descriptor — the meta-type that defines what a composition is — is a blob in substrate.blob, governed by the same 22 triggers as everything else. It is turtles, but finite turtles. The recursion bottoms out at the constitutional layer: BIG_BANG.sql creates the laws. GENESIS enrolls the types. The types then govern all future enrollment.

VI

The Living Machinery

Beneath the constitution, four subsystems give the kernel its pulse. They are not applications. They are not microservices. They are constitutional machinery — patterns that emerge from the trigger chain and the composition system working together.

The Event Outbox

Every mutation to substrate.blob emits a structured event via the i_auto_emit_event trigger. Events land in substrate.event_outbox — a staging table with about, kind, actor, subscribers, is_public, and birthplace columns. External consumers call flush_event_outbox() to mark batches as processed. reap_event_outbox() cleans up after seven days. The outbox is the substrate's nervous system — every change, every enrollment, every retirement is recorded, timestamped, attributed, and made available for downstream processing. No polling. No webhooks. Just a table that knows what happened and who needs to know.

The NLA Queue

The Natural Language Activation queue is the bridge between text and geometry. When any blob with a content or description field is enrolled, the trg_nla_enqueue trigger automatically creates a queue entry. Workers call nla_dequeue() — which uses FOR UPDATE SKIP LOCKED for safe concurrent processing — extract holodot vectors from the content, write them back to the blob's holodot column, and call nla_complete(). If a worker crashes mid-processing, nla_reap_stale() resets stuck entries after one hour. The pipeline is ready. The 578 libraries are waiting. When the NLA workers spin up, every piece of knowledge in the substrate will get a neural fingerprint — a 3,584-dimensional vector that enables semantic search, similarity discovery, and constitutional proximity measurement.

The Vault

Sealed secrets. The vault_entry composition is enrolled and open (arbitrary fields). vault_list() returns names, scopes, and timestamps. vault_unseal(p_name) returns the raw value. Simple. The vault does not do encryption at the SQL layer — that is the caller's responsibility. What the vault provides is constitutional governance of secrets: a vault entry is a blob, which means it has sovereignty (only the creator can read it), immutability guarantees (it appears in the event chain), and compositional validation (the type system ensures it carries the right fields). The lock on the vault is not cryptographic. It is constitutional.

The Pipe Kings Engine

1,344 dataflow nodes — 336 each of consumer, pump, pipe, and mapper — plus 390 adaptors. These are the Pipe Kings topologies: directed acyclic graphs that define how data flows through the system. Every pipeline in MythOS is a topology: fleet dispatch, voice synthesis, diagnostic sweeps, timing analysis, chassis initiatives, complex operations, federation, messaging, money flows, infrastructure ops. Each is enrolled as a set of blobs, wired together by the topology enrollment functions, and executed by the pg_pipe_kings background worker. Force triggers materialize topologies automatically when their conditions are met. The substrate doesn't run pipelines. It grows them.

VIII

What the Kernel Represents

Strip away the poetry. Strip away the metaphors. What is actually sitting on a single AMD 7900 XT desktop in a home office in Georgia?

A self-governing database. Not a database with an application on top. Not a database behind an API. A database that governs itself. The 22 triggers are not optional middleware that some application developer decided to add. They are the kernel. They are the reason the system exists. They enforce identity, sovereignty, type safety, immutability, auditability, and reactivity at the storage layer — before any application code touches the data. The constitution lives inside the database, not above it.

A type system defined in its own data. The 90 compositions are not a schema migration. They are not a config file. They are blobs. The thing that defines what a blob can be is itself a blob. This reflexive property means the substrate can evolve its own type system through the same constitutional process it uses for everything else: INSERT a new composition blob, and the universe gains a new type. No deploy. No migration. No restart. Just a new blob that passed 22 triggers.

A sovereignty model that scales. Sixteen principals governing 8,573 entities, with zero ownership disputes, zero permission bugs, zero "who changed this?" mysteries. The sovereignty model is so simple it almost isn't a model: you own what you create. The trigger checks it. That's the entire access control system. No RBAC. No ABAC. No policy engine. Property law.

A physics engine for data. The AFTER trigger chain means that every write has consequences. Create a library blob with content, and the NLA queue receives work. Create any blob, and the event outbox records it. Create a force-bound blob, and the Pipe Kings topologies materialize. The substrate is not passive storage. It is a reactive system. Blobs don't just sit there. They ripple.

A 33-megabyte civilization. The word is not chosen lightly. A civilization is a set of shared rules, shared identities, shared types, shared history. The substrate has all four. It has constitutional laws that cannot be changed. It has principals with sovereign identity. It has a type system that defines what can exist. It has an immutable event chain that records everything that has ever happened. It is governed, typed, identified, and audited. It is 33 megabytes. It runs on one machine. And it is ready for traffic.
